# 찬호형 피드백 정리

> 옆자리 쌤(Pleos Side-Coach) 개발 방식에 대한 피드백 · 2026-11-15

---

## 1. 잘한 점

- **Git과 Claude로 만드는 방식 자체는 좋았다.** 이슈와 브랜치로 관리되고 있어서 체계적이다. Git 정리는 아직 필요하다.
- **결과물의 큰 틀(와꾸)이 괜찮다.**

## 2. 개선할 점 (핵심)

> **프로젝트를 어떻게 설계할지, 저장소에 무엇을 저장할지, 큰 프로젝트를 하려면 어떻게 설계하고 관리해야 하는지.**

---

## 3. 프로젝트 진행 순서: 어려운 것부터 검증하기

아이디어가 생기면 다음 순서로 진행한다.

1. **기술 검증**
   - 아이디어를 실현하는 데 필요한 **가장 어려운 기술부터** 먼저 검증한다.
2. **시각화 (목업)**
   - 검증이 끝나면 간단히 시각화한다.
   - 이때는 기술을 구현하지 않고 **화면 이미지만 먼저** 만든다. 이걸 목업이라고 부른다.
3. **개발**
   - 무엇을 만들지, 그게 가능한지 **이미 다 확인한 상태에서** 개발을 시작한다.

---

## 4. 저장소 관리: 책상 정리하듯이

### 4.1 기본 태도
- 저장소를 Claude에게 맡겨두고 **데이터 백업 장소처럼 쓰지 않는다.**
- 책상을 정리한다고 생각하고 **착착 정리해둔다.**
- 목표는 **무엇이 어디에 있는지 내가 아는 것**이다.
- 파악이 끝나면 **README나 docs에 "어디에서 무엇을 봐야 하는지"를 문서로** 남긴다.

### 4.2 사람이 읽을 문서와 Claude가 읽을 문서를 나눈다
- 두 종류의 문서는 **따로 저장한다.**
- **사람이 읽을 문서**는 직접 다 읽어보고 **좋은 것만 남긴다.**
  - 그냥 두면 Claude가 아무 한국말이나 막 넣는다.
  - 예: "A 스펙 빼"라고 하면 문서에 "A 스펙은 빠졌다" 같은 **변경 히스토리까지 적어 넣는다.**
  - 사람용 문서는 **지금 상태만** 깔끔하게 담아야 한다. 이런 히스토리 문장은 걸러낸다.

---

## 5. 코드 구조: 코드도 책상 정리 대상이다

책상 정리는 문서와 코드를 단순히 정돈하는 게 아니다. **코드도 책임별로 나눠서** 모듈이나 패키지로 구성한다.

| 책임 | 하는 일 |
|---|---|
| **SDK 연결** | SDK와 연결하는 부분 |
| **상태 분석 / 전처리** | SDK에서 받은 정보로 현재 상태를 분석하고, 시스템에 넘길 형태로 데이터를 가공하는 부분 |
| **기능별 구현** | 시스템이 제공하는 기능별로 구현한 부분 (예: 실시간 조언, 운전 평가서) |
| **진입점** | 시스템이 처음 시작되는 부분 |

- 코드를 한 줄씩 읽지 않더라도 **모듈과 패키지 이름만 보고 책임이 드러나게** 정리한다.
- 책임이 어떻게 나뉘어 있는지, **각 부분이 무엇을 담당하는지는 내가 파악하고 있어야 한다.**
- 그러려면 **로직이 내 머릿속에 들어 있어야 한다.**

---

## 6. Claude와 일하는 태도

- 항상 Claude에게 **"해줘"라고 하지 말고, 먼저 "어떻게 할 거야?"라고 묻는다.**
- 답을 듣고 **이해한 다음에** 넘어간다.

---

## 7. 한 줄 요약

> **어려운 기술부터 검증하고, 목업으로 확인한 뒤 개발한다. 저장소와 코드는 책임이 보이게 정리하고, 그 구조는 내가 이해하고 있어야 한다. Claude에게는 맡기기 전에 먼저 묻는다.**

## 부록: 옆자리 쌤에 적용하면 (내 제안)

> 이 부분은 찬호형 피드백이 아니라, 피드백을 지금 프로젝트에 적용하기 위해 정리한 실행 항목이다.

### A. 진행 순서 점검
- **기술 검증 단계는 이미 일부 했다.** 에뮬레이터 실측으로 조향각, 깜빡이, 브레이크, 차속을 확인했다.
- **아직 검증 안 된 어려운 기술**이 남아 있다.
  - NaviHelper 이벤트가 에뮬레이터에서 실제로 들어오는지 (상황 예고 코칭의 핵심)
  - AAOS 기어, 차속, 비상등 값을 앱에서 읽을 수 있는지
  - 녹음 음성을 오디오 포커스 정책대로 재생하는 것
  - 이 세 가지를 먼저 검증한다.
- **목업**: 기획서의 화면 목업 3장(주행 중, 튜토리얼, 성적표)을 기준 화면으로 확정하고 개발한다.

### B. 저장소 구조 (안)
```
pleos-side-coach/
├─ README.md            ← 사람용: 앱 소개, 실행 방법, "어디서 뭘 보는지" 안내
├─ docs/                ← 사람용 문서 (직접 검토한 것만)
│  ├─ concept.md        ← 무엇을 왜 만드는지
│  ├─ architecture.md   ← 모듈 구조와 책임
│  └─ test-guide.md     ← 에뮬레이터 테스트 방법
├─ .claude/             ← Claude용 문서 (규칙, 참고자료, 작업 메모)
│  ├─ rules/
│  └─ reference/        ← Pleos 가이드 요약, 실측 데이터, API 명세
├─ CLAUDE.md
├─ app/                 ← 코드
└─ github/              ← 툴킷
```

### C. 코드 패키지 구조 (안)
| 패키지 | 책임 (피드백 5장) |
|---|---|
| `data/` (vehicle, navi, ux) | **SDK 연결**: Vehicle SDK, NaviHelper, AAOS API를 구독 |
| `domain/state/` | **상태 분석·전처리**: 신호를 `DrivingSnapshot`으로 가공 |
| `feature/coach/` | **기능**: 실시간 조언 (깜빡이 누락, 급제동, 상황 예고) |
| `feature/report/` | **기능**: 운전 평가서 (오늘의 성적표) |
| `feature/tutorial/` | **기능**: 내 차 익히기 |
| `app/` (MainActivity, Service) | **진입점** |

### D. 다음에 할 일
1. Claude Code에게 **"현재 패키지 구조와 각 패키지의 책임을 설명해줘"**라고 묻고, 위 표와 비교한다.
2. `docs/`의 사람용 문서를 **직접 읽고**, 변경 히스토리 문장(예: "~는 빠졌다")을 걸러낸다.
3. Claude용 참고 자료는 `.claude/reference/`로 옮긴다.
4. README에 **"어디서 무엇을 보는지"** 안내를 적는다.
5. 앞으로는 이슈를 맡기기 전에 **"어떻게 구현할 거야?"를 먼저** 묻는다.
